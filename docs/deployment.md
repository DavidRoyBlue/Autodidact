# Deployment & Run Runbook

How to run and ship Autodidact — dev and prod, backend and mobile. Reference detail lives in
[`gcp_infra_setup.md`](gcp_infra_setup.md) (GCP/Terraform) and
[`apps/mobile/CLAUDE.md`](../apps/mobile/CLAUDE.md) (EAS invariants); this file is the operator view.

**Status legend:** ✅ wired and verified · ⚠️ wired but unverified · ❌ needs wiring

## 1. Local dev (daily loop)

| What | Command | Status |
|---|---|---|
| Backend stack (Supabase + api/agent/worker) | `pnpm dev` | ✅ |
| Mobile in **Expo Go** on the Windows-host emulator | `pnpm mobile:run` (or `pnpm mobile` for Metro only) | ✅ |
| First-time setup | `pnpm setup` | ✅ |

`pnpm mobile:run` boots the AVD (`Medium_Phone`), starts Metro, sets up `adb reverse` for
ports 8081 (Metro), 3000 (api), 55321 (Supabase), and opens the app in Expo Go.

**Known limit of Expo Go:** native modules are absent. Since social sign-in
(`@react-native-google-signin/google-signin`, imported by `src/lib/social-auth.ts` via
`UpgradeAccountCard`) landed, the app **crashes on boot in Expo Go** with
`'RNGoogleSignin' could not be found`. Day-to-day dev now requires the **dev client** below.

## 2. Mobile dev client (custom dev build)

A dev client is a custom APK containing the app's native modules + `expo-dev-client`; JS still
comes from Metro, so the daily loop is unchanged once it's installed. Required for any native
module — today that's Google sign-in. Full auth setup: [`apps/mobile/docs/social-sign-in.md`](../apps/mobile/docs/social-sign-in.md).

**Current status: ❌ no dev client exists.** The only attempt (EAS build, 2026-06-24) failed in
prebuild: `app.json` references `./assets/icon.png`, `./assets/splash.png`,
`./assets/adaptive-icon.png` but `apps/mobile/assets/` does not exist. The production build
attempt (2026-06-17) failed on the same missing assets. Fix = add the three images (see
shortcomings below), then:

```bash
cd apps/mobile
eas build --profile development --platform android   # cloud build, ~15 min
# download the APK from the printed URL, then:
adb install <apk>                                    # onto the emulator
pnpm mobile                                          # Metro; open the project from the dev-client launcher
```

Rebuild the APK only when native deps or `app.json`/plugin config change; JS iterates via Metro.

What's wired for it already:

## Environment wiring summary

`app.config.ts` resolves `extra.*` at Metro/build time: build-profile env (`eas.json`) →
`.env.dev` (local Metro) → `app.json` fallbacks. Consequences:

- Local Metro (`pnpm mobile`/`mobile:run`): local Supabase stack + `localhost:3000` API — matches
  `pnpm dev`. ✅
- EAS `preview`/`production`: Cloud Run API via profile env; Supabase falls back to the **hosted**
  project baked in `app.json`. ✅ (intended)
- EAS `development` **installed APK launched without Metro**: localhost API + hosted Supabase
  fallback — mixed targets, but irrelevant in practice because a dev client is always driven by
  Metro, which re-resolves from `.env.dev`. ⚠️ just don't treat a standalone-launched dev client
  as a working app.
