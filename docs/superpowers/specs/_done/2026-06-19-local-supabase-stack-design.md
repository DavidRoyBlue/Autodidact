# Local Supabase Stack — Design Spec

**Date:** 2026-06-19
**Status:** Draft (brainstorming) — pending review, then implementation plan
**Position:** **Spec 1 of 4.** Foundational infra; unblocks local testing of everything that follows (Production Auth → Onboarding course → DEV_AUTO_LOGIN).

> **Hard constraint (commit `fa73ba8`, [`packages/db/CLAUDE.md`](../../../packages/db/CLAUDE.md) §Invariants):** *Drizzle is the sole migration authority — all schema changes go through `packages/db/migrations/`. The root `supabase/` directory is for Supabase CLI tooling only; the CLI must NOT own a parallel `supabase/migrations/` trail.* This spec is bound by that invariant; see D1.
>
> **Already on master (`fa73ba8`):** the root `supabase/` workspace exists and is linked to `cbzdsoojfhpsexuyeyxt` — `config.toml` (default) + `.gitignore` committed, `.temp/` gitignored. The stray `apps/mobile/supabase/` was deleted; there is exactly **one** Supabase CLI workspace (repo root). So `supabase init`/`link` are **done**; this spec only *configures* it.

## Problem

Local development today is a **hybrid**: data runs on a local Docker Postgres (`pgvector/pgvector:pg16`, port 5432), but **auth runs against the shared *cloud* Supabase project**. Consequences:

- The local DB has only **stub `auth.uid()` / `auth.role()` functions** (`docker/dev-db-init.sql`) so RLS migrations *compile*; there is no real local GoTrue. You cannot test real auth behavior locally — signup, email confirmation, anonymous sign-in, JWT claims, RLS-with-real-`auth.uid()` — all require the cloud project.
- Auth experiments therefore mutate a **shared cloud project**, and auth config (GoTrue settings) is dashboard-only, not version-controlled.
- The upcoming work (anonymous sign-in, GoTrue hardening, RLS consistency, DEV_AUTO_LOGIN) is hard or impossible to develop/test without a real local auth stack.

## Goal

Local dev runs the **full Supabase stack via `supabase start`** (Postgres + GoTrue + PostgREST + Studio), so the entire auth surface is real and local. **"Local for dev, prod for prod."** Auth/config becomes config-as-code (`supabase/config.toml`). The cloud project `cbzdsoojfhpsexuyeyxt` is reserved for production.

## Non-goals

- Changing the **migration tool**. Drizzle remains the schema source of truth (see D1).
- Containerizing the Node services (they keep running natively via `turbo run dev`).
- Any auth *feature* work (anonymous sign-in, provisioning, hardening) — that's Spec 2. This spec only stands up the stack and wires config/env/scripts so Spec 2 is testable.
- pgvector extension relocation (deferred project-wide).

## Verified current state (foundation)

- `docker-compose.yml`: single `pgvector/pgvector:pg16` Postgres, `autodidact` db, `postgres/password`, port 5432, init via `docker/dev-db-init.sql`.
- `docker/dev-db-init.sql` (12 lines): creates `vector` + `uuid-ossp` extensions and **stub** `auth` schema with `auth.uid()` → zero-UUID and `auth.role()` → `'authenticated'`. Compile-time only; backend connects as superuser and bypasses RLS.
- **Migrations are Drizzle** (`drizzle-kit`), in `packages/db/migrations/` (`0001`–`0005` + journal v7), reading `DATABASE_URL`. `db:generate` / `db:migrate` wrappers in `packages/db/package.json`.
- pgvector is integrated via a custom Drizzle type (`packages/db/src/vector.ts`, `vector(1536)`); `CREATE EXTENSION vector` lives in `0001_initial.sql` *and* the init file.
- Env (`.env.dev`): `DATABASE_URL` → local Docker (`localhost:5432`); `SUPABASE_URL`/keys → **cloud** project. `AUTH_PROVIDER=supabase`.
- **`supabase` CLI v2.107.0 is already a devDependency**, but there is **no `supabase/` dir or `config.toml`** and no `supabase` scripts. Greenfield CLI adoption.
- Scripts: `scripts/{setup,dev,migrate,db-reset,db-studio,gen-migration,stop}.sh`.

## Decisions & drivers

- **D1 — Drizzle is the SOLE migration authority** ([`packages/db/CLAUDE.md`](../../../packages/db/CLAUDE.md), commit `fa73ba8`). **All** schema changes — `public` tables **and** auth-schema-touching objects (the `handle_new_user` trigger on `auth.users`, RLS policies / `ENABLE RLS`, `GRANT`/`REVOKE`, helper functions referencing `auth.jwt()`/`auth.uid()`) — go through **`packages/db/migrations/`**. Public-table changes are generated by `drizzle-kit`; auth-touching objects are authored as **hand-written custom SQL migrations** in the *same* trail (the existing `0003_rls.sql` / `0004_rls_fixes.sql` already apply RLS this way). **There is NO `supabase/migrations/` trail; never run `supabase migration new`, `supabase db diff`, or `supabase db reset` to manage schema.** The root `supabase/` directory is **CLI-tooling only**: local dev-stack runtime, GoTrue/auth settings in `config.toml`, edge functions, `supabase gen types`, remote linking. *(This corrects an earlier draft of this spec that proposed splitting schema into `supabase/migrations/` — now explicitly forbidden.)*
- **D1a — Auth-touching DDL still lives in Drizzle migrations even though it references the `auth` schema.** Drizzle migrations are plain SQL applied by `drizzle-kit migrate`; a hand-authored migration can `CREATE FUNCTION` / `CREATE TRIGGER ... ON auth.users` / `GRANT`. The "Drizzle owns `public`" idea is about the *tool*, not a hard schema boundary — the deploy artifact is the single `packages/db/migrations/` trail.
- **D2 — `DATABASE_URL` points at the local Supabase Postgres, direct, on `127.0.0.1:54322`** (`postgresql://postgres:postgres@127.0.0.1:54322/postgres`). The local `postgres` role has `BYPASSRLS` — matching prod, so the API's RLS-bypass behavior is identical local and prod.
- **D2a — The port-6543 transaction-pooler invariant is scoped to CLOUD/prod only; local is exempt.** That invariant ([`packages/db/CLAUDE.md`](../../../packages/db/CLAUDE.md)) exists because the *cloud* direct host (`db.<ref>.supabase.co:5432`) is IPv6-only and unreachable from WSL2. The local stack listens on `127.0.0.1:54322` (no pooler, reachable directly), so that rationale does not apply. Local dev connects direct to `54322`; the pooler URL remains required for the prod `DATABASE_URL`. Document this exemption next to the invariant.
- **D3 — `supabase/config.toml` is the source of truth for *local* auth/config.** How it propagates to **prod** is an **OPEN question**, not a settled decision: `supabase config push` may not cover all needed settings in CLI v2.107.0. Until verified (see Open items), assume prod config is applied via the dashboard and treat config.toml↔prod parity as **manual + documented**.
- **D4 — Retire `docker-compose.yml` + `docker/dev-db-init.sql`.** The local Supabase stack supplies the real `auth` schema and functions, so the stubs are obsolete; extensions are created by Drizzle migrations.
- **D5 — Local Supabase keys/URL come from env**, not hardcoded. Backend reads `.env.dev`; mobile resolves them through `app.config.ts` (no cloud values hardcoded in `app.json` for dev).

## Architecture / components

### 1. Configure the (already-linked) Supabase CLI workspace
- `supabase init` + `supabase link --project-ref cbzdsoojfhpsexuyeyxt` are **already done** (commit `fa73ba8`): `supabase/config.toml` (default) + `.gitignore` are committed, `.temp/` gitignored.
- **Do NOT create `supabase/migrations/`** (D1). It must not exist.
- Tune `config.toml`: confirm `[db] major_version = 16` and ports (`api = 54321`, `db = 54322`, `studio = 54323`); set `[auth] site_url` + `additional_redirect_urls` for the mobile scheme; `jwt_expiry`; email/signup baseline. **Keep auth config minimal here** — Spec 2 tunes anonymous sign-in, confirmations, rate limits.
- **`supabase/seed.sql`**: create as a **no-op placeholder** (header comment only). It must stay a no-op because (a) `supabase db reset` would auto-run it *before* the Drizzle schema exists (wrong order — see component 7), and (b) real app/test-user seeding (Spec 4) runs as a **post-migrate script step**, not via the CLI's auto-seed. Defer content; keep the file inert.

### 2. Env changes (`.env.example` + `.env.dev`)
- `DATABASE_URL` → `postgresql://postgres:postgres@127.0.0.1:54322/postgres`.
- `SUPABASE_URL` → `http://127.0.0.1:54321` (local API gateway).
- `SUPABASE_PUBLISHABLE_KEY` / `SUPABASE_SECRET_KEY` → the local stack's keys, as printed by `supabase start` (well-known local dev keys).
- Keep a documented **prod** profile (cloud URL + pooler `DATABASE_URL`) for migrating/operating prod — clearly separated from dev.

### 3. Mobile → local auth (dev)
- `app.config.ts` resolves `SUPABASE_URL` + publishable key from env for dev instead of the hardcoded cloud values in `app.json`.
- **Android emulator caveat:** the emulator reaches the host via `10.0.2.2`, not `127.0.0.1`. The dev Supabase URL the *app* uses must be `http://10.0.2.2:54321` (mirroring how the app reaches the API today). Document this mapping; reuse the existing emulator host approach (see `apps/mobile` README / `run-mobile`).
- (Detailed mobile auth-flow changes belong to Spec 2/4; this spec only ensures the dev URL/keys are env-driven and emulator-reachable.)

### 4. Scripts rewrite
- `setup.sh`: replace `docker compose up -d` + `pg_isready` wait with `supabase start` (+ readiness wait). Keep pnpm install, `.env` copy, migrate, build.
- `dev.sh`: `supabase start` instead of `docker compose up`; then build, `pnpm migrate:dev` (Drizzle), `turbo run dev`.
- `migrate.sh`: **remove** the `dev-db-init.sql` re-apply block (stubs gone); run `drizzle-kit migrate` against `DATABASE_URL` (works for local *and* prod).
- `db-reset.sh`: `supabase db reset` resets ONLY to the clean Supabase baseline (empty `public`; its auto-run of the inert `seed.sql` is harmless) → **then** `drizzle-kit migrate` (app schema + auth-touching objects) → **then** the post-migrate seed step (Spec 4). Keep the localhost-only guard. `supabase db reset` is **never** the schema source.
- `stop.sh`: `supabase stop` (preserve data) instead of `docker compose down`.
- `db-studio.sh`: keep Drizzle Studio; note Supabase Studio is also available at `:54323`.
- Delete `docker-compose.yml` and `docker/dev-db-init.sql`.

### 5. Extensions
- Drizzle migration `0001` already `CREATE EXTENSION IF NOT EXISTS vector`. Confirm it resolves on the Supabase local image (Supabase ships `vector`; `IF NOT EXISTS` is a safe no-op if pre-created in the `extensions` schema and on `search_path`). Audit whether `uuid-ossp` is actually used (schema defaults use built-in `gen_random_uuid()`); drop it if vestigial.

### 6. Docs
- Update root `README.md` + `CLAUDE.md` command tables (`pnpm setup`/`dev`/`stop`/migrate now drive `supabase start`).
- Update `apps/mobile` docs for the local-Supabase auth URL + emulator host mapping.
- Note `supabase/config.toml` as the local auth-config source of truth and the prod-mirroring approach.

### 7. Local DB schema & seed wiring (explicit — answers "how does the local stack get its schema?")

The local Supabase Postgres is schema-populated by **the existing Drizzle trail, run against it** — *not* by `supabase db reset`/`supabase/migrations` (which don't carry app schema, per D1):

1. `supabase start` → boots the local stack with an **empty `public`** schema (plus Supabase's internal `auth`/`storage`/etc.).
2. `scripts/migrate.sh` → `drizzle-kit migrate` against `DATABASE_URL=…@127.0.0.1:54322/postgres` applies `packages/db/migrations/` (`0001`→latest), creating `public` tables and (from Spec 2 onward) the auth-touching objects.
3. **Seeding** (Spec 4's `test@autodidact.dev`, any baseline data) runs as a **post-migrate step in our scripts** — *after* step 2 — never via the CLI's auto-seed. `config.toml` extension/auth settings are CLI-owned; schema and seed orchestration are ours.

This wiring is the load-bearing answer the constraint demanded: **CLI provides the runtime + auth; Drizzle provides the schema; our scripts sequence them.**

## Error handling / edge cases
- `supabase start` requires Docker; preserve the prereq check in `setup.sh` with a clear message.
- Port conflicts (54321–54323) — document overrides in `config.toml`.
- First `supabase start` pulls several images (slow once); note it.
- Migrations must be idempotent/clean on a fresh Supabase baseline (they already run from `0001`).

## Testing / verification
- `supabase start` boots; `supabase status` shows healthy services.
- `drizzle-kit migrate` applies all migrations on the local stack with no error; `vector(1536)` columns create successfully.
- Backend connects via local `DATABASE_URL`; existing API integration tests pass against the local stack.
- A real signup/login against **local** GoTrue returns a valid JWT whose `auth.uid()` resolves in SQL (proves the stub removal is correct).
- `db-reset.sh` returns the local DB to a clean migrated state.

## Risks
- **Resource usage:** `supabase start` runs many containers (heavier than one Postgres). Acceptable for a dev box; note it.
- **Mobile emulator networking:** host `127.0.0.1` vs `10.0.2.2` for both API and Supabase — a known foot-gun; document clearly.
- **Hardcoded cloud values in `app.json`:** must move to env via `app.config.ts` or dev mobile auth will still hit the cloud project.
- **Extension schema divergence:** `vector` may live in `extensions` (local Supabase) vs `public` (prod). Deferred concern (pgvector move is out of scope), but verify the type resolves locally.
